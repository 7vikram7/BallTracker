# Working on BallTracker: a guide for other people and agents

Everything needed to understand, test and improve this project without access to the original
machine. If you are an agent asked to review or suggest improvements, start here.

## 1. What this is and what matters

Live line calling for pickleball. Phones around the court detect the ball, and a 2020 Intel
MacBook (no GPU) fuses the cameras and speaks **OUT** or **FAULT**. It stays silent when unsure.
The project started as a learning project, and the aim is an installation at a club.

* **Priorities:** live line calls, then stats, then coaching.
* **Policy: silent unless sure.** A wrong OUT is far worse than a missed one. Every change is
  judged first by *wrong OUT calls* (must stay 0), then by *OUTs announced*.
* **Hardware on hand:** iPhone 17 (120 fps app, 240 fps Slo-mo), iPhone 16, Samsung (app, about
  60 fps), a few budget Androids (12-30 fps), and the Intel MacBook.
* **Licences:** no AGPL or GPL, and nothing non-commercial (no Ultralytics YOLO). MIT, BSD and
  Apache are fine.
* **Privacy:** the repo is public. No camera images of people, no personal names, no
  credentials.

Background: [PROJECT_BRIEF.md](PROJECT_BRIEF.md) is the original brief (much broader: multi-sport).
[DECISIONS.md](DECISIONS.md) records what was actually decided and why. [ARCHITECTURE.md](../ARCHITECTURE.md)
describes the design.

Formats: `balltracker/live/session_log.py` (session folders), `balltracker/live/protocol.py`
(wire format), `balltracker/events.py` (event schemas). In `dets.jsonl`, each line is one frame:
`{"seq", "tp" (phone clock, s), "ts" (session clock, s), "w", "h", "c": [[u, v, radius_px, score], ...]}` (all ball
candidates the phone found).

**Live decisions vs replays.** During field test 2 the Mac was overloaded and dropped about 19 000
frames (fixed since; FIELD_TEST_2_RESULTS.md). A replay processes every frame, so it makes about
1 060 decisions where the live run made 605. Compare a change by replaying before and after, not
against the live decisions. The full session takes about 30 min of CPU on the 2020 Intel Mac;
`scripts/slice_session.py` cuts shorter pieces.

**Not in the repo, and why:**

* Camera images and video (field-test frames 1.7 GB, the 240 fps clip 600 MB): people can be
  visible and the files are large. What tests need from them is in the repo instead: per-frame
  detections of every session, and per-frame candidates of both detectors for the 240 fps clip.
  Ask the owner if you need actual images (detector training, line detection).
* Conversation transcripts, TLS keys and credentials. The motivation is in DECISION_LOG.md.

`scripts/export_for_repo.py` regenerates `data/field/` from the local machine; personal details
are removed by `scripts/hooks/privacy.py`.

## 4. Running things

```bash
.venv/bin/pip install -e ".[dev,live]"
pytest -m "not slow"                                  # ~4 min
pytest                                                # full, ~8 min; must pass before any commit
bt replay data/field/20261119-070916                  # real session, current code
.venv/bin/python scripts/lob_study.py --quick         # lobs, 4 cameras, ~3 min
.venv/bin/python scripts/lob_study.py --rig 2good+2weak --no-reducer   # camera set-ups
bt live-demo --edge                                   # simulated phones end to end
```

The golden tests (`tests/test_golden.py`, data in `tests/golden/`) pin exact live decisions on real data. A change that
moves them needs a stated reason.

## 5. Open problems worth working on

Each one has data in the repo and a measurable target.

1. **Far-half calibration bias.** In field test 2, the Samsung put far-half bounces 0.7-1.5 m from
   where the iPhone put them; near-half bounces agreed within 6-18 cm. Shared-bounce refinement
   (`geometry/crosscal.py`) cuts this to 21-49 cm on held-out bounces. *Target:* < 10 cm on the
   far half. *Data:* `data/field/20261119-070916` (pairs of reports in `events.jsonl`, type `report`).
2. **Uncertainty is underestimated.** Per-camera velocity covariance underestimates the error
   by about 3x (median |z| ≈ 3, LOB_STUDY.md), which is why `VEL_SIGMA_FLOOR_PX` exists. Position
   covariances may have the same problem. *Target:* calibrated z-scores on field and simulated
   data, without adding wrong OUTs.
3. **Close calls stay silent.** Bounces 3 cm out are rarely announced with two cameras (1 of 8 in
   CAMERA_RIGS.md). Can fusion or the bounce fit get tighter without risking wrong OUTs?
4. **Weak-camera veto.** A camera that can see the spot but misses the bounce silences an OUT.
   Weight the veto by each camera's measured recall (CAMERA_RIGS.md, last section).
5. **Detector.** Classical colour + motion (`edge_detection.py`, mirrored in C++ in `mobile/`).
   False candidates: the clutter numbers are in `camera_stats` events. Any learned model must
   keep the licences clean and run on the phone.
6. **Fully automatic calibration** (no taps) fails at the real venue (neighbouring courts and
   nets); "Snap to lines" from 4 rough taps works (`geometry/autocal.py`). Images are needed to
   work on this; ask the owner.

## 6. How to propose a change

* State the problem with numbers from the data above, the change, and **before/after numbers**
  from `bt replay` on field test 2 and from the lob study: wrong OUTs, OUTs announced, false
  decisions, position error.
* Keep the full `pytest` passing. Add a test that fails without your change.
* Small, separate changes beat one large one. Update DECISIONS.md if a decision changes.
